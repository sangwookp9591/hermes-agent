# ADR-001 — 멀티 에이전트 오케스트레이션은 Hermes Kanban을 채택한다

- 상태 **Accepted**
- 날짜 2026-09-04
- 결정자 hermess 설계
- 관련 [ADR-002](ADR-002-coordination-boundaries.md) · [ADR-003](ADR-003-model-routing.md) · [ADR-004](ADR-004-external-integration.md)

## 맥락

`hermess-arch.md`는 다음 구조를 직접 만들 것을 전제했다.

```
AI Orchestrator → Router / Coordinator → Claude/Codex/Gemini Bot → Independent Reviewer
```

실측 결과(`hermess-design-review.md` §2.5) 이 구조가 **Hermes Kanban으로 이미 구현되어 있고
오늘 동작한다.** 우리가 만들려던 것과 목표가 겹친다.

또한 Kanban 스펙이 명시적으로 겨냥한 워크로드가 우리 요구사항과 일치한다 —
리서치 트리아지, 스케줄 운영, 디지털 트윈, **엔지니어링 파이프라인(분해 → 병렬 구현 → 리뷰 → 반복 → PR)**.

## 검토한 선택지

**A. Kanban 채택** — 커널 그대로 쓰고 프로필·스킬만 작성
**B. 차용 재구현** — 스키마/디스패처 설계를 베껴 자체 구현
**C. delegate_task만으로 구성** — 보드 없이 위임 트리로 해결
**D. 제외** — 외부 오케스트레이터(Airflow/Temporal 등) 도입

## 결정

**A를 채택한다.**

## 근거

**1. 실행으로 검증됐다.** P2 파이프라인을 실제 구동해 의존성 해석 → 원자적 claim →
프로세스 spawn → 부모 결과 전달 → 자동 승격까지 전 구간을 확인했다. 문서 신뢰가 아니라 실측이다.

**2. C(delegate_task 단독)는 우리 요구를 구조적으로 못 채운다.** 스펙 §10의 12개 축 중
치명적인 것:

| | delegate_task | 우리 요구 |
|---|---|---|
| 감사 추적 | **컨텍스트 압축 시 소실** | 리뷰 이력이 남아야 함 |
| 재개 | 없음. 실패 = 실패 | 부분 실패에서 재개 |
| 사람 개입 | 불가 (headless) | 애매하면 물어봐야 함 |
| 태스크당 에이전트 | 1개 | 구현 → 리뷰 → 재구현 (N개) |

**3. B(재구현)의 비용이 정당화되지 않는다.** 커널은 스펙 주장(4테이블)보다 큰
**7테이블 / 37컬럼**이고, 서킷 브레이커·크래시 회수·heartbeat·stale-claim 회수·run 이력이
이미 들어 있다. 이걸 다시 만드는 건 우리 문제 해결이 아니다.

**4. D(외부 오케스트레이터)는 축이 다르다.** Airflow/Temporal은 결정론적 워크플로 엔진이고,
Kanban은 **에이전트 정체성 + 메모리 + 스킬**을 1급으로 다룬다. 우리가 필요한 건 후자다.

**5. MIT 라이선스**라 막히면 언제든 B로 후퇴할 수 있다. A가 되돌리기 쉬운 선택이다.

## 결과

**얻는 것** — 커널 코드 0줄. 우리가 작성할 것은 프로필 정의와 스킬뿐이다.
**포기하는 것** — 아래는 커널이 제공하지 않으므로 직접 만들거나 포기한다(스펙 §14).

| 필요 기능 | 실현 방법 |
|---|---|
| smart routing / auto-assignment | `router` 프로필 (user-space) |
| 예산 제한 | spawn 래핑 플러그인 |
| 승인 게이트 | `tools/approval.py` 재사용 |
| 대시보드 | 대시보드 플러그인 |

**감수하는 제약**
- **single-host 설계.** 위협 모델이 trusted-local-user다. 분산이 필요해지면 ADR을 다시 연다.
- **폴링 지연.** 디스패처 tick 기본 60초 → 의존성 해소~워커 기동까지 최대 60초.
- **스펙-구현 드리프트.** PDF는 "DESIGN ONLY"이고 실제 구현은 더 크다.
  **PDF는 설계 근거로만 쓰고 사실은 코드로 확인한다.**

## 재검토 트리거

- 분산 실행이 요구사항이 될 때
- 60초 지연이 문제가 될 때
- upstream이 Kanban을 breaking change 하거나 폐기할 때
